# Rollin 使用手册 · 活动负责人与管理员

> 适用角色：活动负责人（OWNER）、活动管理员（ADMIN）。适用版本：V1。
> 界面文案、字段限制、报错行为均按当前代码实际实现书写，未实现的功能单列在 §8。
>
> 文中 `[📊 ...]` 是留给你补的真实信息，比如域名、联系方式、截图位置。这些只有你知道，我没有替你编。

---

## 0. 先记三件事

**这个系统只负责"发 Offer、等回复、缺人补位"。** 名单从哪来它不管，你把名单导进去就行。

**负责人管规则，管理员管日常。** 差别集中在 quota、发放模式、SMTP、成员、Import Token、审计这六块，其他页面对双方一样。

**有两个按钮按下去就回不了头：**「确认启动」和「确认归档」。其余操作基本都能补救。

## 2. 上手

### 2.1 激活账号

负责人由平台管理员邀请，管理员由本活动的负责人邀请。流程一样：收到邮件 → 点链接 → 设置密码 → 直接进入活动工作区。

密码要求：至少 8 位，必须同时有字母和数字，不超过 72 字节。邀请链接 72 小时内有效；同一个成员重复发起邀请，旧链接立刻失效。

### 2.2 登录

地址：`[📊 填管理后台地址]` + `/login`。

要填三项：活动标识、邮箱、密码。

活动标识就是 URL 里 `/a/` 后面那段，比如 `tech-dept-2026`。小写字母、数字、短横线，3 到 64 位。忘了标识问负责人。

**同一个邮箱在不同活动里是两个独立账号。** 密码各管各的，你在技术部改的密码不影响宣传部那个账号。所以别指望一套密码走遍所有活动。

系统没有找回密码功能。忘了只能请负责人（或平台管理员）重发一封邀请邮件。

### 2.3 左侧菜单

| 菜单 | 用途 |
| --- | --- |
| Dashboard | 全局概览与告警 |
| 候选人 | 查名单、筛选、改分 |
| 排名 | 重算排名、处理同分 |
| Offer | 启动录取、发放、重发、递补、批次记录 |
| 邮件 | 发送任务状态与失败重试 |
| 活动设置 | quota、发放模式、有效时长、成功提示、归档 |
| SMTP | 活动发件邮箱配置 |
| 成员 | 管理员邀请、重发邀请、停用 |
| Import Token | 外部系统导入名单的凭证 |
| 导出 | 下载 XLSX |
| 审计 | 关键操作留痕 |

### 2.4 第一件事：配好 SMTP

**别跳过这步。** 没配 SMTP，AUTO 模式连正式录取都启动不了（会报 `SMTP_NOT_CONFIGURED`），Offer 邮件也发不出去。

要填的字段：服务器地址、端口、加密方式、用户名、密码、发件人。

加密方式怎么选？看端口：

- 587 端口 → 选 `STARTTLS`（先明文连接再升级，最常见）
- 465 端口 → 选 `SSL` 或 `TLS`（连接即加密）
- `无加密` 只在本机调试时用，生产环境别选

发件人格式写成 `Rollin <noreply@example.edu.cn>` 这种带名字的形式，候选人收到的邮件会显示得正式些。

填完点「发送测试邮件」，收到才算通过。密码在库里是加密存储的，界面上也不再回显；以后修改时密码框留空就表示不改原密码。

## 3. 一场招新的完整流程

```
配 SMTP
  ↓
创建 Import Token → 交给外部报名系统
  ↓
外部系统逐人导入名单
  ↓
核对名单、改错分
  ↓
重算排名
  ↓
处理同分顺序
  ↓
启动正式录取（排名永久冻结）
  ↓
系统 / 人工发放 Offer → 候选人接受 / 放弃 / 超时
  ↓
自动递补或人工补发
  ↓
导出数据留档
  ↓
归档活动
```

**顺序不能乱，有两个死结：**

第一，**重算必须在调同分之前**。重算会把所有手工同分调整清掉。

第二，**导入必须在启动录取之前**。启动后排名冻结，导入接口直接返回 `RANKING_FROZEN`，改分、重算、调序全部停用。

## 4. 各模块怎么用

### 4.1 Dashboard

顶部徽章一眼看清活动状态、发放模式、排名是否冻结、是否有待重算、递补是否暂停。

中间的统计卡：录取容量、当前占用、已接受、待确认、已放弃、已超时、候补、已失格、已发 Offer 总数、失败邮件、待发送邮件。

**当前占用 = 已接受 + 待确认（Offer 口径）**，这个数字永远不能超过 quota。

下面可能出现四种告警，处理优先级从高到低：

1. **排名待重算**：有人导入或改过分，去「排名」页点重算，否则启动不了录取。
2. **自动递补已暂停**：释放的名额不会自动补位。确认情况后由负责人点「恢复递补并补齐空额」。
3. **有 N 封邮件发送失败**：去「邮件」页挨个重试。
4. **尚未启动正式录取**：排名没冻结，还能改分、调序、导入。

### 4.2 候选人

列表显示排名、姓名、邮箱、学号、分数、状态、Offer 情况、Offer 截止、邮件状态、导入序号。

排序：点「排名 / 分数 / 导入序号 / 导入时间」表头切换升降序。筛选：状态下拉 + 搜索框（姓名、邮箱、学号都认）。每页 20 条。

**改分**：点候选人行的「改分」，填新分数。规则是 1 到 2147483647 的正整数，改完会打上「排名待重算」标记，界面上会提示你去重算。

分数从哪来？从外部系统的导入数据来。你在这里改分，本质上是在纠错，不是在评分。排名冻结后改分按钮会禁用。

### 4.3 排名

**重算排名**：按分数从高到低、同分按导入顺序，生成连续的 1 到 N。点「重算排名」会先弹确认框，提醒你所有手工同分调整将被清除且不可恢复。

**同分顺序调整**：只列出有同分的分组，一组一组处理。每组可以上移下移，改完点「保存该组顺序」。「还原」按钮放弃本组未保存的改动。

两条铁律：只能在同一个分数组内挪，不能跨分；整组顺序要一次提交完。想让 91 分的人排到 90 分后面？系统不允许，这是设计上的红线。

冻结后这两个功能都变灰。超过 1 万条候选人时列表会提示不完整。

### 4.4 Offer

这是最核心的一页。

#### 三种发放模式

| 模式 | 启动后首发 | 有人放弃或超时后 | 谁在动手 |
| --- | --- | --- | --- |
| AUTO 自动滚动 | 按 rank 自动发满 quota | 系统自动补下一位 | 系统 |
| BATCH 分批发放 | 不自动发，点「发放下一批」按 rank 整批发 | 不自动补，需要再点一次 | 人工点按钮 |
| MANUAL 手动发放 | 不自动发，逐个挑人 | 不自动补，需要逐个发 | 人工挑人 |

怎么选？名额固定、想让系统跑完就选 AUTO；想分批观察候选人质量选 BATCH；需要对每个人单独判断选 MANUAL。

MANUAL 模式允许不按排名发，比如先给第 10 名再给第 3 名。但 `已接受 + 待确认 ≤ quota` 这条上限，任何模式都不能破。AUTO 模式下系统不许手动单人发放，点击会提示「AUTO 模式下系统按 rank 自动滚动，不允许手动发放」。

**模式在启动正式录取后锁定，改不了。**

#### 启动正式录取

点「确认启动」之前，系统会检查这几项：

- 活动处于运行中（ACTIVE）
- quota ≥ 1
- 排名已同步，没有待重算的改动，且所有人的 rank 都已生成
- 活动里至少有一个启用的负责人
- **AUTO 模式额外要求 SMTP 已配置且验证通过**（BATCH 和 MANUAL 不要求）
- 你勾选了「我已了解」的确认框

**启动 = 排名永久冻结，不可撤销。** 之后不能改分、不能重算、不能调同分、不能再导入、不能切换模式。启动前请把名单核对到你自己觉得不会再变了。

#### 手动发放（MANUAL）

点「手动发放 Offer」，搜出候选人，点确认。后端会依次检查七件事，任何一条不过都会被拒：

活动在跑 / 排名已冻结 / 当前是 MANUAL 模式 / 此人还是「候补中」 / 此人没在别的活动接受过 Offer / 本活动没给过他有效 Offer / 当前占用没满。

#### 邮件重发 vs 特殊重新发放

这两个容易混，看清楚了再用：

| | 重发邮件 | 特殊重新发放 |
| --- | --- | --- |
| 什么时候用 | Offer 还是「待确认」，但对方说没收到 | Offer 已是「已放弃」或「已超时」，你想再给一次机会 |
| 结果 | 同一封 Offer 再发一次 | 生成一张**新** Offer |
| 状态与截止时间 | 都不变 | 截止时间重新计算 |
| 权限 | 负责人和管理员 | 仅负责人 |
| 要不要写原因 | 不用 | 要，1 到 500 字，写进审计日志 |

**重发不延长截止时间。** 这是最容易踩的坑：候选人今天到期，你上午重发一次邮件，他下午还是过期。要延长时间只能走特殊重新发放。

#### 恢复递补

递补被暂停时（比如活动被禁用后重新激活），Dashboard 会出现提示，负责人可以在 Offer 页点「恢复递补并补齐空额」，系统按排名把空位补上。

#### 批次历史

BATCH 模式下页面下方有批次记录，能看到每批发了多少人、谁操作的、什么时候发的。

### 4.5 邮件

列出所有发送任务：任务编号、类型、收件人、状态、重试次数、下次重试时间、最后错误、发送时间。

状态含义：

- `待发送`：排队中
- `发送中`：正在发
- `已发送`：成功
- `发送失败`：达到重试上限
- `已取消`：不再发送（比如活动被禁用时统一取消）

**自动重试策略**：最多重试 8 次，间隔从 1 分钟开始每次翻倍，最长 1 小时。

超过 8 次都没成功，状态变成「发送失败」，行尾出现「重试」按钮。点一下重新排队，重试次数清零。但有个前提：对应的业务对象还得是可发送的（比如那封 Offer 仍是「待确认」）。如果 Offer 已经过期，重试会被拒，得走特殊重新发放。

失败邮件堆积时，先看「最后错误」列。常见原因是 SMTP 认证失败或对方邮箱不存在。前者去 SMTP 页检查配置，后者得改候选人邮箱（在改分同一个对话框里改）。

### 4.6 活动设置

- **录取容量 quota**（负责人）：填个整数，不能小于当前占用。上调时的行为分模式：AUTO 会自动补齐空额（递补暂停时先记下意图）；BATCH 不自动发，需要你去 Offer 页点「发放下一批」；MANUAL 同样要人工发。
- **Offer 发放模式**（负责人）：启动前可切换，启动后显示「已锁定」。
- **Offer 有效时长**：只读。由平台管理员创建活动时设定，活动内改不了。
- **Offer 确认成功提示**（双方可改）：候选人在 Accept 成功页看到的文案，最多 500 字符，留空保存就是清除。团队有后续安排就写在这里，比如「欢迎加入技术部，请留意第一次例会通知」。
- **归档活动**（负责人）：见 §7。

### 4.7 SMTP

负责人专属。管理员打开这个页面只会看到一句提示：SMTP 由负责人统一管理。

字段和填写要点见 §2.4。修改配置、发送测试都会记审计。

### 4.8 成员

列出全部成员：姓名、邮箱、角色、成员状态、账号状态、邀请状态、加入时间。

负责人可以「邀请管理员」：填姓名和邮箱，系统发一封邀请邮件（走活动 SMTP，72 小时有效）。同一个人重复邀请会让旧邀请失效，这是正常的，不是 bug。

停用管理员时可以随时操作，但停用立刻生效：对方手上的登录状态马上失效，不用等会话过期。停用只影响权限，数据都留着。

### 4.9 Import Token 与外部对接

**Import Token 是给外部报名系统用的凭证，不是给人用的。** 谁需要往你的活动里推名单，就把 Token 给谁。

创建时填两项：备注名（可选，写清用途方便以后辨认）、过期时间（可选，不填默认 7 天）。

**Token 原文只在创建成功时显示一次。** 服务端只存哈希，关掉提示窗就再也查不到。丢了就吊销重建，别想找回。

状态有三种：有效、已吊销、已过期。过期是自动判定的，不用定时任务。

导入表单的下方有完整的接口说明，可以直接把那段复制给外部系统的对接人。

#### 接口细节

```
POST /api/import/candidates
Authorization: Bearer rt_xxxxxxxx
Content-Type: application/json
```

请求体是单个对象：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| `studentId` | 是 | 1 到 64 位，只允许字母、数字、下划线、短横线；前导零保留；导入后不可修改 |
| `name` | 是 | 不超过 100 字 |
| `email` | 是 | 不超过 254 字符，会转成小写 |
| `score` | 是 | 1 到 2147483647 的整数 |
| `qq` | 否 | 不超过 32 字符 |
| `className` | 否 | 不超过 100 字 |

curl 示例：

```bash
curl -X POST https://[📊 管理后台域名]/api/import/candidates \
  -H "Authorization: Bearer rt_xxxxxxxxxxxxxxxx" \
  -H "Content-Type: application/json" \
  -d '{
    "studentId": "2023001234",
    "name": "张三",
    "email": "zhangsan@example.edu.cn",
    "score": 92,
    "className": "软件2301"
  }'
```

**一次只能传一个人。** 100 个人就调 100 次，传数组会被拒绝。

**接口是幂等的，可以放心重试。** 同一个 `studentId` 重复提交，内容一模一样就返回现状不做改动；内容有变化就原地更新，并打上「排名待重算」。所以外部系统遇到超时可以直接重发，不会产生重复候选人。

返回 `201` 表示新建，`200` 表示命中已有记录，响应里带 `created`、`applicationId`、`candidateId`、`activityId`、`status`、`rankingDirty`。

限流：每个 Token 每分钟 60 次。批量导入上百人时注意加速度，撞上限流会返回 `RATE_LIMITED`，等一分钟再继续。

排名冻结后 Token 仍然可以创建，但导入会被拒（`RANKING_FROZEN`）。要做大批量导入，务必在启动正式录取之前完成。

### 4.10 导出

点一下直接下载 XLSX，文件名格式是 `活动标识-candidates-20260923.xlsx`（当天的日期）。

包含 16 列：学号、姓名、班级、邮箱、QQ、分数、排名、导入顺序、Offer 状态（当前或最近一次）、Offer 来源、Offer 发送时间、Offer 接受时间、Offer 放弃时间、Offer 放弃原因、Offer 超时时间、报名时间。放弃原因是候选人拒绝时选填的自由文字（最长 500 字），没填就是空白。表里所有时间都是北京时间（UTC+8）。

导出的表格首行冻结（往下滚动列名不消失），表头带筛选按钮，可以直接按「Offer 状态」筛选；Offer 状态和来源列的值与管理端徽章文案一致（待确认、已接受、已放弃、已超时；Offer 来源为自动、分批、手动、特殊）。

学号列是文本格式，前导零不会丢，这点对学号带 0 开头的学校很重要。

两个限制：超过 5 万行会被拒绝；活动被禁用时导不了。**归档后仍然可以导出**，所以留档不着急。

### 4.11 审计

负责人专属。记录关键操作，可以按动作名（比如 `OFFER_ISSUED_MANUAL`）和时间范围筛。

每页 50 条，列出时间、操作者（含角色）、动作、目标、摘要。系统自动做的事（自动发放、Offer 过期、跨活动联动放弃）也会记录，操作者显示为「系统」。

有争议的时候先来这里看。谁在什么时候把 quota 从 20 改成 25，都留痕。

## 5. 候选人那头看到什么

候选人不需要注册、不需要登录，点开邮件里的链接就是全部交互。所以你回复咨询之前，先知道对面看到的是什么。

| 情况 | 候选人看到 |
| --- | --- |
| 待确认 | 「录取通知」抬头、正文、确认截止时间、剩余时间（不足 1 小时变警示色）、两个按钮 |
| 已接受 | 「你已接受本次录取」，下面显示你配的那段成功提示 |
| 已放弃 | 「你已放弃本次录取资格」，提示无法自行恢复，需联系组织方 |
| 已超时 | 「已超过确认截止时间」，显示原截止时间 |
| 活动被平台禁用 | 「Offer 已失效 / 该录取通知当前无法查看或处理」 |
| 活动已归档 | 只读展示录取结果，无操作按钮 |
| 链接错误 | 「访问受限 / 链接无效或已失效」 |

待确认页底部有一句系统提示：「接受后将自动放弃你在其他活动中已获得的录取资格。」这句话是自动的，不用你解释，但候选人经常来问，你可以直接引用。

## 6. 报错怎么处理

| 报错码 | 意思 | 怎么办 |
| --- | --- | --- |
| `VALIDATION_ERROR` | 字段不合格 | 对照 §4.9 的字段表和页面提示改 |
| `RANKING_FROZEN` | 排名已冻结 | 录取启动后这就是终态，改不了。只能新建 Offer 走特殊流程 |
| `RANKING_DIRTY` | 有导入或改分没重算 | 去「排名」页点重算排名 |
| `MODE_LOCKED` | 启动后想切模式 | 不允许。设计如此 |
| `QUOTA_EXCEEDED` | 名额已满 | 先提高 quota，或等有人放弃释放名额 |
| `QUOTA_TOO_SMALL` | quota 低于当前占用 | 改回去，或先处理掉待确认和已接受的 Offer |
| `SMTP_NOT_CONFIGURED` | 活动 SMTP 没配好 | 去 SMTP 页配置并测试通过（AUTO 模式启动录取的硬性条件） |
| `OFFER_NOT_ACTIONABLE` | 这张 Offer 已经处理过了 | 是被重复点击触发的，看当前状态即可 |
| `OFFER_EXPIRED` | Offer 已过截止时间 | 要重新给机会就走「特殊发放」，别用重发邮件 |
| `ACTIVITY_DISABLED` | 活动被平台禁用 | 联系平台管理员，只有他能重新激活 |
| `ACTIVITY_ARCHIVED` | 活动已归档 | 只读终态，无法恢复 |
| `TOKEN_INVALID` / `TOKEN_EXPIRED` | 令牌无效或已过期 | Import Token 重新创建一个 |
| `RATE_LIMITED` | 频率超限 | 导入每 Token 每分钟 60 次，等等再试 |
| `EXPORT_TOO_LARGE` | 导出超过 5 万行 | 分期导出，或找开发同学协助 |
| `EMAIL_TAKEN` / `MEMBER_EXISTS` | 邮箱或成员已存在 | 该成员已在活动里，用「重发邀请」而不是重新创建 |
| `FORBIDDEN` | 权限不足 | 这个操作属于负责人专属，找负责人 |

## 7. 不可逆操作清单

动这几处之前，先把这句话读一遍：**系统不提供撤销。**

1. **启动正式录取**：排名永久冻结。不能改分、不能重算、不能调同分、不能导入、不能换模式。
2. **归档活动**：永久只读，不能重新激活。归档前必须没有「待确认」的 Offer，有的话按钮点不动。
3. **quota 下调**：不能低于当前占用（已接受 + 待确认）。
4. **Import Token 创建**：原文只显示一次，关掉就找不回。
5. **手动发放的 Offer**：一旦发出，状态不能改回候补。只能等候选人放弃或等到过期。
6. **候选人放弃 Offer**：不能由候选人自行恢复。要再给机会，负责人走「特殊发放」新建一张。
7. **过期 Offer**：不能靠「重发邮件」复活。名额可能早就给别人了。
8. **停用管理员**：对方立即失去访问权限，虽然可以重新邀请，但中间的操作记录会显示停用时段。

另外提醒一句：有人接受 Offer 后，他在其他活动里的待确认 Offer 会被系统自动置为「已放弃」，那些活动各自的递补机制会跟着跑。这个联动是自动的，不需要谁去点。

## 8. 界面上暂时没有的功能

诚实列出来，免得你到处找。

- **邮件模板没有编辑页面。** 后端接口已经具备（`GET/PUT /api/activities/{slug}/mail-templates`），支持变量 `{{candidateName}}`、`{{activityTitle}}`、`{{offerUrl}}`、`{{expiresAt}}`、`{{siteName}}`，主题不超过 200 字符、正文不超过 10000 字符。界面入口还没做，需要改文案得找开发同学走接口。
- **Offer 有效时长在活动内只读。** 由平台管理员创建活动时设定（1 到 720 小时）。当前代码也没有修改端点，要调整需要开发介入。
- **审计日志只显示摘要**，不展开 detail 原文。需要完整变更内容得从数据库或补接口取。
